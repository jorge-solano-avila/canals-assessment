# Canals — Order Service

A backend service that creates orders: it geocodes the shipping address, picks the single nearest
warehouse able to supply **every** requested product, atomically reserves the stock, charges a
payment provider, and confirms the order — with idempotency, compensation and a transactional
outbox.

One endpoint: **`POST /orders`**.

---

## 1. Prerequisites

**You do not need Python installed.** Everything — the app, migrations, seeds, tests, even
dependency locking — runs inside containers. This is deliberate: the project targets Python 3.12,
and the machine it was developed on has 3.8.

| Software | Minimum | Why | Check with |
|---|---|---|---|
| **Docker Engine** | 20.10+ | runs every service | `docker --version` |
| **Docker Compose** | **2.1.1+** | `make test` uses `up --wait`, added in 2.1.1 | `docker compose version` |
| **GNU Make** | any | the entry point for every command | `make --version` |
| **curl** *(optional)* | any | for the smoke test below | `curl --version` |

Docker Desktop (macOS/Windows) bundles Compose v2, so on those platforms Docker Desktop plus the
`make` that ships with the OS is the whole list. On Linux install `docker-ce`, the
`docker-compose-plugin` package, and `make`.

Verify in one go:

```bash
docker --version && docker compose version && make --version | head -1
```

### Resources and ports

- **~2 GB of disk** for the images (`postgis/postgis:16-3.4` is the large one) and **~1 GB of RAM**
  while running.
- **Three host ports must be free**, or changed in `.env` — see [§7 Troubleshooting](#7-troubleshooting):

  | Port | Service | `.env` variable |
  |---|---|---|
  | 5432 | PostgreSQL + PostGIS | `POSTGRES_HOST_PORT` |
  | 55433 | test database | `POSTGRES_TEST_HOST_PORT` |
  | 8000 | the API | `APP_HOST_PORT` |

- **Your Docker daemon must be running.** `docker info` should succeed before you start.

## 2. Setup

Four commands from a fresh clone:

```bash
cp .env.example .env     # 1. create your local config
make up                  # 2. build the image, start db / db-test / app
make migrate             # 3. create the schema (Alembic; never create_all)
make seed                # 4. load products, warehouses, inventory, a customer
```

`make up` takes a few minutes the first time — it pulls PostGIS and builds the app image.
Afterwards it is seconds.

**Expected output from `make seed`:**

```
Seeded 5 products, 4 warehouses, 14 inventory rows, 1 customer, 2 addresses.
```

Confirm everything is healthy:

```bash
docker compose ps
```

`db` and `db-test` should both say `(healthy)`.

### What the four commands do

- **`cp .env.example .env`** — the only manual step. `.env` is gitignored; `.env.example` is
  committed and documents every variable.
- **`make up`** — builds from `Pipfile.lock` with `pipenv install --system --deploy`, which *fails
  the build* if the lock file has drifted from the Pipfile.
- **`make migrate`** — migrations are **never** run automatically on container start. Applying them
  is always an explicit, visible step.
- **`make seed`** — idempotent. Re-running never duplicates rows and never overwrites `reserved`,
  so it cannot corrupt live reservations.

## 3. Run it

```bash
make run
```

Serves on the port in `APP_HOST_PORT` (8000 by default), with auto-reload. Then:

- **API docs:** <http://localhost:8000/docs> — FastAPI's interactive UI, the fastest way to explore
- **Health:** <http://localhost:8000/health>

```bash
curl -s localhost:8000/health
# {"status":"ok","checks":{"database":"ok"}}
```

`make run` holds the terminal. Open a second one for the commands below, or run the API detached:

```bash
docker compose exec -d app uvicorn app.main:app --host 0.0.0.0 --port 8000
```

### Place an order

The seeded ids are regenerated by every `make reset`, so fetch them rather than copying them:

```bash
make psql
```

```sql
SELECT id AS customer_id FROM customers;
SELECT sku, id AS product_id, unit_price_minor FROM products ORDER BY sku;
\q
```

Then POST, substituting the two ids:

```bash
curl -i -X POST localhost:8000/orders \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: my-first-order' \
  -d '{
    "customer_id": "<customer_id>",
    "shipping_address": {
      "line1": "Calle de Alcala 45",
      "city": "Madrid",
      "postal_code": "28014",
      "country_code": "ES"
    },
    "items": [{"product_id": "<SKU-KEYB product_id>", "quantity": 2}],
    "card_number": "4242424242424242"
  }'
```

Expect **`201 Created`**, a `Location: /orders/{id}` header, and a body with `"status":
"confirmed"`.

> **`Idempotency-Key` is required.** Sending the request without it returns `400`. Reuse the *same*
> key and you get the original order back without a second charge; that is the point.

### Test cards

The mock provider is deterministic — behaviour comes from the **last four digits**, the same
convention real gateways use. Nothing is random, so a reviewer re-running this gets identical
results.

| Card number | Outcome | What happens |
|---|---|---|
| `4242424242424242` | succeeds | order `confirmed`, stock sold, outbox event written |
| `4000000000000002` | declined | `402`, stock **released**, order `payment_failed` |
| `4000000000000069` | timeout | `502`, stock **stays held**, order stays `reserved` |
| `4000000000000119` | provider error | `502`, same as timeout |

The timeout case is the interesting one: the outcome is *unknown*, not failed, so releasing the
stock would risk losing the order of a customer who was actually charged. See [§6](#6-design-notes).

### Things worth trying

| Do this | Get this |
|---|---|
| Send the same body and key twice | `201` both times, identical body, **one** charge |
| Same key, different body | `422 idempotency_key_conflict` |
| Omit the `Idempotency-Key` header | `400` |
| Order the 4K monitor (`SKU-MON27`) | selected warehouse flips to **SVQ-01** — Seville is the only one that stocks it, 390 km away, and completeness beats distance |
| Order more than the stock on hand | `409 insufficient_stock` |

## 4. Testing

```bash
make test
```

Starts the dedicated `db-test` service, applies migrations to it, and runs the suite with coverage.
It works from nothing — no need to `make up` first.

**35 tests**, ~86% coverage against an 80% floor. They run against **real PostgreSQL + PostGIS**,
never SQLite: the selection query uses PostGIS, and the concurrency tests depend on real row-level
locking and `READ COMMITTED` semantics that no in-memory database reproduces.

Notable ones:

- ten coroutines race for the **last unit in stock** — exactly one wins, and the test asserts the
  ten used *different* database connections, so it cannot pass vacuously
- twenty concurrent multi-item orders over overlapping products complete **without deadlock**
- the same idempotency key sent concurrently creates **one** order and **one** charge
- a declined payment restores inventory to its exact prior counts
- the card number appears in **no** log record

The test database uses `tmpfs`, so it is fast and starts clean on every restart.

## 5. Commands

```bash
make            # (no default target; the list below is the whole interface)
```

| Command | What it does |
|---|---|
| `make up` | build and start `db`, `db-test`, `app` |
| `make down` | stop everything, **keeping** the database volume |
| `make migrate` | apply migrations to head |
| `make seed` | load reference data (idempotent) |
| `make run` | serve the API (host port = `APP_HOST_PORT`) |
| `make test` | run the suite against `db-test` |
| `make psql` | interactive PostgreSQL shell |
| `make logs` | follow service logs |
| `make sweep` | release expired stock reservations |
| `make outbox` | publish pending outbox events |
| `make revision m="..."` | autogenerate a migration |
| `make lock` | regenerate `Pipfile.lock` (runs in a container) |
| `make reset` | **destructive** — delete the database volume |

### Background jobs

`make sweep` and `make outbox` are **entrypoints, not daemons**. Nothing runs them automatically —
run them by hand, from cron, or as their own compose service. They are separate processes rather
than background tasks inside the API so they execute exactly once regardless of how many API
workers exist, and cannot take the API down with them.

- **`make sweep`** returns stock from reservations whose hold expired
  (`RESERVATION_TTL_SECONDS`, 15 minutes by default). It is also the backstop for a payment whose
  outcome is never resolved.
- **`make outbox`** publishes `order_confirmed` events. The publisher is a **log sink** — CLAUDE.md
  forbids external brokers, so the port keeps the broker-shaped seam without the dependency.
  Delivery is **at-least-once**: publishing happens inside the claiming transaction, so a crash
  after publishing but before commit republishes. Consumers must be idempotent.

## 6. Design notes

The interesting decisions, with the reasoning in the code rather than here.

**The payment call never sits inside a transaction.** The sequence is
`reserve → commit → charge → commit`. An open transaction across a network call of unbounded
duration would hold row locks on `inventory` for its whole length.
[`order_checkout.py`](app/services/order_checkout.py) asserts `session.in_transaction() is False` at
the moment the provider is invoked, so a future refactor that wraps the saga in one transaction
fails loudly instead of silently degrading throughput.

**Unknown is not failure.** A provider timeout leaves the payment `pending`, the order `reserved`
and the stock **held**, with the idempotency key still `in_progress` so a retry gets `409` rather
than a second charge. Releasing stock on an unknown outcome is how a customer who *was* charged
loses their order. `reconcile_payments.py` is the job that asks the provider afterwards; the full
loop is out of scope and marked as such.

**Stock reservation is one atomic conditional UPDATE**, never read-check-write:
`WHERE on_hand - reserved >= :qty ... RETURNING`. Zero rows means insufficient stock. Correctness
rests on `READ COMMITTED` re-evaluating the `WHERE` clause against the new row version when a
blocked UPDATE resumes — which is why the guarantee is documented as deliberately
PostgreSQL-specific in [`reservation.py`](app/repositories/reservation.py).

**Deadlocks are prevented by ordering, not retries.** Every statement that updates `inventory` does
so sorted by `(warehouse_id, product_id)`. Removing that sort makes the concurrency test fail with
`DeadlockDetectedError`, which is how the ordering was verified rather than assumed.

**Warehouse selection is advisory.** It is a read with no locking, so the chosen warehouse may lose
its stock before the reservation runs. The reservation is the sole authority; selection only narrows
the field. On losing that race the request fails fast rather than retrying — a client retry re-runs
selection against fresh data, which beats looping over candidates already known to be stale.

**The card number is never stored or logged.** Only `card_brand` and `card_last4` are persisted;
there is no column capable of holding a PAN. In transit it is a Pydantic `SecretStr`
(`repr()` renders a mask), excluded from serialization, and kept out of validation errors by
`hide_input_in_errors=True` — without which a failure on *any* field could echo the number into a
422 body. `get_secret_value()` is called in exactly two places, neither of which logs.

**Money is always integer minor units** plus a currency column. `order_items` snapshots price,
currency, SKU and name at purchase time, so rendering an old order never joins back to `products`
and picks up today's price.

### Layout

```
app/
  api/          routes, dependency wiring, exception handlers, logging
  services/     orchestration — imports ports, never adapters, no FastAPI
  repositories/ SQLAlchemy data access; receives a session, never commits
  ports/        Protocols: GeocodingProvider, PaymentProvider, EventPublisher
  adapters/     mock implementations of those ports
  models/       SQLAlchemy tables
  schemas/      Pydantic request/response
  domain/       enums, errors, value objects, the state machine
  jobs/         standalone entrypoints (sweeper, outbox relay, reconciliation)
  db/           engine, session factory, geography helpers
migrations/     Alembic; hand-reviewed, never autogenerate-and-ship
tests/          real PostgreSQL, truncation between tests
```

## 7. Troubleshooting

**A port is already in use** — the most common problem. `make up` fails with
`bind: address already in use`. Find the culprit and change the matching variable in `.env`:

```bash
lsof -nP -iTCP:5432 -sTCP:LISTEN     # who has 5432?
```

```bash
# .env — any free port works; only the host side changes
POSTGRES_HOST_PORT=55432
APP_HOST_PORT=8005
```

Then `make down && make up`. Nothing inside the containers changes — they talk to each other on the
compose network.

**`make test` says the database is unreachable** — `db-test` may not be up yet.
`make test` starts it with `--wait`, but if you ran `pytest` directly, start it first:

```bash
docker compose up -d --wait db-test
```

**Apple Silicon: a platform warning on `db`.** `postgis/postgis:16-3.4` publishes no `arm64` image,
so it runs under emulation:

```
The requested image's platform (linux/amd64) does not match the detected host platform
```

It works correctly, just slower. Harmless for development.

**`make migrate` says "Can't locate revision"** — usually a database from an older schema. Reset it:

```bash
make reset && make up && make migrate && make seed
```

**Orphan container warning** after changing compose services:

```bash
docker compose up -d --remove-orphans
```

**Start completely over:**

```bash
make reset && make up && make migrate && make seed
```

## 8. Not included

Deliberately out of scope, and stated rather than hidden:

- **Retries against the payment provider** — a timeout is resolved by reconciliation, not by
  retrying blindly.
- **The full reconciliation loop** — the unknown state, the provider query and the resolution
  branches exist; scheduling, backoff and alerting do not.
- **A real message broker** — the outbox relay publishes to a log sink behind a port.
- **Authentication, authorization and rate limiting.**
- **Management APIs** for customers, products or warehouses — the brief excludes them, which is why
  `make seed` is the only way reference data enters the database.

**Redis was specified and then removed.** The brief's stack listed it as a geocoding cache, but the
geocoder is an in-process mock — the cache saved nothing and cost a service, a port, an adapter and
a degradation path to maintain. It belongs back the moment geocoding becomes a real network call,
and the `GeocodingProvider` port is the seam where a caching decorator would slot in. The removal is
recorded in `CLAUDE.md` alongside the project's other deliberate amendments.
